## 1. 目标与既有设计的关系

用户先了解社区和流程，选择全新玩家或经验玩家申请，提交完整资料。审核通过后，沿用邮件邀请、验证码验证、完善账号和登录的方向。申请阶段不收集密码，不创建正式账号。

本设计修订 `.notes/archive/join-registration/specs/2026-09-27-join-registration-design.md` 与 `.notes/archive/join-registration/rfcs/join-registration-rfc.md` 中的三个产品决定：

| 既有决定                       | 本次确认后的决定                                                     |
| ------------------------------ | -------------------------------------------------------------------- |
| `/join` 整页三步申请表         | 展示页与两个申请入口，分别打开分步 Modal                             |
| 申请仅收集邮箱、名字、QQ       | 保留旧页全新玩家、经验玩家两套完整资料、问题、承诺和可选证明附件     |
| 拒绝后可重新申请，排除公开查询 | 两类申请共用邮箱唯一规则，拒绝后不能再次提交；新增邮箱直接查询结果页 |

其余邀请资格、验证码、完善凭证、账号创建、登录和 SSO 生命周期沿用既有邀请注册设计；不借申请展示页重新设计这些流程。后续 RFC 需核对开发时的最新邀请注册契约，不能把旧文档与本次差异混合实现。

通用配置式表单已另行交接至 ExWebsite 主工作区的 `.notes/todos/2026-09-27-configurable-forms-and-join-handoff.md`。该交接的组件归属和公开 API 仍是建议；本设计不授权 ExUI 库开发、迁移或发布，也不把尚不存在的 `@exre/exui/forms` 当作现有 API。申请表仍须使用 RHF、Zod 与 ExUI，可通过共享字段定义和配置消费后续通用能力。

## 2. 加入展示页

### 2.1 路由与布局

`/join` 位于站点 `RootLayout` 内，保留顶栏、主题和既有 Join 导航。

宽屏采用已确认的 A 布局：顶部标题与简介；主体左侧为申请须知、加入流程、Q&A 和保持联系，右侧为两个申请入口与结果查询入口。右侧可随滚动保持可见，但不能覆盖顶栏或超出可用视口。

窄屏采用单列，顺序固定为标题与简介 → 两种申请入口上下排列 → 申请须知与加入流程 → Q&A 与保持联系。查询入口跟随申请入口呈现。分栏切换采用与站点一致的 `52rem` 窄屏边界；极窄视口不设置导致横向溢出的固定最小宽度。

使用新的 ExUI 组件、CSS Modules、现有 token 与 lucide 图标，支持浅色、深色和 system 主题。视觉保留草图的清晰层级、留白、轻量边框与少量背景氛围；不搬运旧玻璃组件、旧动效依赖或自建 token 系统。

### 2.2 两种申请入口

| 入口         | 说明与行为                                                                              |
| ------------ | --------------------------------------------------------------------------------------- |
| 全新玩家申请 | 适合尚未接触 FiveM、RP 或紧急服务扮演的玩家；打开全新玩家 Modal                         |
| 经验玩家申请 | 适合有其他服务器、RP 或紧急服务扮演经验的玩家；打开经验玩家 Modal；保留旧调转申请的内容 |

两个入口是申请类别，不是两个独立账号或两个可重复申请的名额。表内申请人类型另有成年、未成年、曾任管理和曾任技术四个选项，不能与全新／经验玩家类别合并。

### 2.3 内容与流程

参考 `ex-face` 旧加入页的内容组织：社区指引、加入条件、真实资料、线上面试、后续学院安排和保持联系。结合已确认的邀请注册方向，页面说明：阅读指引与条件 → 选择类别并填写资料 → 等待人工审核与社区安排 → 获批查收邀请 → 验证邮箱并完善账号 → 跟进学院或社区后续通知。

线上面试与学院安排仍由社区人工组织，审核结果接入既有同意／拒绝流程。本期不新增面试排期系统、课程系统或独立面试状态表。

沿用旧页的条件说明：年满 17 周岁且完成高中课程、成熟的理解能力、基本英语能力与清晰表达、不担任直接干涉其他服务器行政事务的主要职务、遵守社区道德与行为规范。经验入口保留旧页对相关经验和 100 小时以上游玩经历的说明。条件作为申请说明与人工审核依据，不因此增加表单中不存在的学历、英语等级或时长证明字段。

Q&A 覆盖无经验申请、申请类别选择、面试安排、无法按时面试、等待期间准备、何时有结果、未满足条件、未收到邀请、重复申请及邀请到期。不得复制旧页中“满足条件后再次申请”的提示；同邮箱重复申请的新规则优先。审核和面试结果不承诺固定时限，以社区实际通知为准。

社区指引与联系方式通过站点配置提供。实现时核对旧页配置中的 QQ、KOOK 地址是否仍有效；本设计不新建 `/guide` 或把不存在的手册页当作可用路由。缺少有效手册链接时，说明通过社区置顶指引阅读，不渲染通向 404 的操作入口。

## 3. 申请 Modal 与响应式交互

### 3.1 步骤

| 类别     | 步骤                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 全新玩家 | 联系方式 → 基本资料 → 玩法认知 → 时间与来源 → 确认提交，共五步              |
| 经验玩家 | 联系方式 → 基本资料 → 过往经历 → 笔试与证明 → 时间与来源 → 确认提交，共六步 |

当前步骤有明确标题和进度。前进只校验当前步骤，未来尚未填写的必填字段不能阻止前进；最终提交验证全部字段和跨字段规则。后退保留资料、选项与文件，确认步骤展示完整分组摘要并允许返回修改。

宽屏可让短字段按组排列两列，长题目、回答、文件列表与承诺占整行。窄屏字段一律单列，长标签、错误和文件名换行。Modal 尺寸适配视口，不沿用旧 `50vw` 配合 `minWidth: 480` 的布局。

标题、进度及底部操作保持可见，内容区独立滚动。键盘焦点限制在 Modal 内，关闭恢复到对应入口按钮；错误与字段建立可访问关联。虚拟键盘、窄屏或高度较小的窗口中仍可到达最后一个字段及操作按钮。

### 3.2 草稿与提交

RHF 管理值、错误、校验与提交状态，Zod 定义规则并接入 resolver。非表单流程状态由外层负责。全新玩家与经验玩家分别使用完整 schema，复用共同字段定义和控件，不维护一份混合的任意 details 对象。

草稿仅在当前 Modal 内存保存；关闭、刷新或真正卸载后清除，重新打开从空表单开始。切换类别时使用新的独立实例，另一类的回答和文件不能进入提交。

只有最后的“提交申请”调用服务端。请求在途时禁用重复提交和关闭操作，直至成功或失败；失败后保留草稿与附件，支持重试。字段错误通过 `setError` 展示，非字段错误在表单层显示。错误消息不得回显数据库路径、SQL、堆栈或内部异常。

成功后在同一个 Modal 中显示“申请已收到”、后续社区安排、查收邮箱和结果查询入口。只有服务端完成资料与附件事务后显示成功。重复申请显示“该邮箱已有申请，不能重复提交”，提供查询入口，不伪装成创建了新申请。已有正式账号且不具备新的申请资格时引导登录，不创建申请。

## 4. 两套完整表单

字段的 HTTP 名称、序列化和 schema 在后续 RFC 与 `api/openapi.yaml` 固化。这里定义业务内容及客户端与服务端都须满足的规则，不创建第二套 DTO。

### 4.1 共用字段

| 步骤       | 字段         | 规则                                                                                                                   |
| ---------- | ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 联系方式   | 名字         | 必填；新手标签“你的名字”，经验玩家标签“IC 名字”；沿用当前昵称 trim、1–32 个 Unicode 码点、禁止控制字符、允许重名的规则 |
| 联系方式   | 邮箱         | 必填；沿用 Contract 的有效邮箱规则，trim 并转小写，最长 254；用于联系、去重、查询与邀请                                |
| 联系方式   | QQ 号码      | 必填；保留旧申请的 5–13 位数字规则，字符串保存前导零；不修改账号资料的 1–20 位规则                                     |
| 基本资料   | 出生日期     | 必填、合法日历日期，不能是未来日期；日期输入不自动改变时区或把日期改成时间戳                                           |
| 基本资料   | 申请人类型   | 必填；普通成年 `100`、普通未成年 `101`、曾任其他服务器管理 `102a`、曾任技术 `102b`                                     |
| 基本资料   | 申请部门     | 必填；警察部门 `leo`、医疗和消防部门 `ems`                                                                             |
| 时间与来源 | 每周空闲时间 | 必填；每晚都有空、每周三天以上、每周三天以下，或自由填写                                                               |
| 时间与来源 | 了解方式     | 至少选择一项，可多选；B站 `bilibili`、抖音 `douyin`、朋友介绍 `friends`、其他 `other`                                  |

资料的出生日期及身份类别供人工审核；通用日期控件不写死社区年龄规则，也不自动推断是否完成高中课程。

### 4.2 全新玩家专属

以下五个问题全部必答：

1. 是否接触过 FiveM，是否游玩过其他 RP 服务器？保留“没有接触过”选项，也可自由填写。
2. 是否对“紧急职业模拟”这一种游玩方式有过了解？保留“了解”“不了解”，也可自由填写。
3. 是否对美国警察执法程序，或紧急救援、医疗处理流程有基本了解？文本回答。
4. 是否知道什么是 RP？提示谈谈自己的理解。
5. 是否知道什么是 FRP？提示谈谈自己的理解。

最终确认三项承诺，均须为 true：资料真实无误；能遵守服务器规定与政策；清楚面试通过进入学院后，因自身原因缺课、旷课所产生的后果由自己承担。承诺属于表单值并保留到申请记录，不用独立 `useState` 控制。

### 4.3 经验玩家专属

过往经历六项全部必填：以前所在服务器；离开原因；以前所在部门；执法生涯经历；最高警衔／等级；是否受过任何形式的处罚。部门保留巡逻、交通、特殊、警探、飞机、医疗、消防选项，也允许自由填写；无处罚须明确回答。

笔试与证明步骤：

| 内容                                         | 规则                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| 是否需要遵循“武力降级”原则？如果是，为什么？ | 必填，trim 后至少 150 个 Unicode 码点                                       |
| 在什么情况下可以使用“自由裁量权”？           | 必填，trim 后至少 150 个 Unicode 码点                                       |
| 为什么应该接受您的调转？                     | 必填文本                                                                    |
| 证明文件                                     | 可选，最多 5 个，单个不超过 10 × 1024 × 1024 字节，支持选择、拖放和粘贴文件 |

允许文件扩展名沿用旧页：`.png`、`.jpg`、`.jpeg`、`.gif`、`.bmp`、`.svg`、`.pdf`、`.doc`、`.docx`、`.xls`、`.xlsx`、`.ppt`、`.pptx`、`.txt`、`.zip`、`.rar`、`.7z`。

文件列表显示名称、大小和移除操作。服务器独立验证数量、大小与类型，不能只信浏览器 accept 或 MIME；不解压压缩文件、不执行或内联呈现证明文档。审核查看采用下载方式。

最终确认“我确认以上信息真实无误”。经验玩家不额外复制新手的两项专属承诺。

其他文本须有明确非空与长度上限，禁止任意大小字符串；具体上限在 RFC 中按短字段／长回答分别固化并与客户端统一。两道笔试题旧代码只有必填校验，新实现必须补上旧题目文案要求的最小字数。

## 5. 保存、附件与去重

### 5.1 一次提交与原子保存

最终请求一次提交完整资料与所选附件，不提前创建申请或数据库草稿。服务端验证完整资料、承诺和文件后，在一个 SQLite 事务中写入申请、回答、承诺与附件。任一验证或写入失败都不留下半份申请、孤立附件或占用该邮箱的无效登记。

申请记录保留稳定标识、规范化邮箱、玩家类别、完整资料与回答、承诺事实、提交时间，以及既有审核状态。不保存申请密码，审核同意不等于已注册。

附件元数据与二进制均保存在固定的 `apps/mock-server/data/mock.sqlite` 内，二进制使用 BLOB；关联具体申请，不新建本地附件目录。最大有效附件总量为 50 MiB，服务端须限制请求大小与同时处理数量，不能放开所有 HTTP operation 的 bodyLimit。传输格式与 Glue／Client 的接入方式由 RFC 固化并通过真实路由验证，不能以现有 4 MiB JSON 请求能力作为“附件已支持”的依据。

本地 SQLite BLOB 是已确认的 Mock 保存方式；未来 PHP/MySQL 的附件物理方案不在本期，但须保持申请与附件的一致性和读取边界。

### 5.2 邮箱唯一

同一规范化邮箱在两个玩家类别及所有审核状态下，只能提交一次申请。重复请求和并发竞争不能覆盖原资料、创建第二条记录或换一个玩家类别重申。拒绝、邀请到期和完成注册不释放申请名额。

唯一性由数据库约束或邮箱唯一登记保证，不能只在客户端禁用按钮或采用先查后写的非原子检查。请求到达最终事务时再次核对，冲突返回安全、固定的已申请提示。

新增迁移保留已有账号、申请和审核历史，不隐式 reset，不为建立唯一约束而删除历史。若旧规则已产生同邮箱多条历史，RFC 必须采用保留历史的唯一登记／兼容方案：新提交全部被阻止；查询按提交时间降序、稳定标识作为同时间次级排序选择最近申请。既有已完成注册关联优先显示完成结果，不被较晚的历史拒绝掩盖。

### 5.3 审核接线

既有审核列表继续使用申请资料、审核与邀请两个 Tab。详情需按两种申请分组展示完整回答、承诺与附件清单，供社区实际审核；列表显示玩家类别以区分申请。

同意、拒绝和重新发送邀请沿用既有生命周期。过期邀请由审核端重新签发，不允许申请人通过再次填表延长资格。邮件投递失败不回滚审核，也不能声称邮件已送达。

临时审核端的访问边界沿用既有 RFC 的本地公开测试方案，不新增管理员初始化或权限系统。它只代表回环 Mock 能力，不证明生产权限或申请资料的生产访问保护；后续权限系统须统一覆盖完整详情与附件读取。

## 6. 申请结果查询

### 6.1 路由与操作

前端查询页使用 `/join/result`，位于站点布局中；`/join` 的查询入口和提交成功界面都指向它。

页面包含返回加入页、简短说明、申请邮箱、查询按钮及当前结果。窄屏单列，按钮不挤压输入框。两个申请类型共用同一查询，不要求先选类别。

邮箱直接查询，不要求登录或验证码。邮箱随请求体发送，不放入查询 URL；不自动查询、不自动发码，不保存查询邮箱与结果到浏览器持久存储。业务层通过生成 Client 调用只读查询 operation。

### 6.2 结果与下一步

| 状态       | 提示与下一步                                                   |
| ---------- | -------------------------------------------------------------- |
| 未查到     | 确认邮箱是否与提交时一致；未申请可返回加入页                   |
| 待审核     | 已收到申请，保持联系并等待社区安排；可再次主动查询             |
| 已通过     | 前往完善注册；验证码从邀请邮件获取，未收到可按既有注册流程重发 |
| 已拒绝     | 本次未通过，不能再次提交；需要了解后续安排时联系社区           |
| 邀请到期   | 已获批但邀请到期，联系社区重新发送；无需重填申请               |
| 已完成注册 | 前往登录                                                       |

“已通过”不能被前端解释成“邮件已送达”。有效邀请与投递失败分别记录；过期与完成状态由服务端基于当前时钟和实际邀请／账号关联计算。查询响应的具体字段和状态枚举由 RFC 固化，前端不能自己合成审核状态。

查询响应只包含展示所需的结果和下一步，不包含申请 ID、名字、QQ、出生日期、答案、承诺内容、附件、审核人、内部投递错误、验证码、邀请标识或完善凭证。注册入口不能夹带验证码或授权凭证。

用户已选择只输入邮箱即可查询，因此知道邮箱的人可以知道其申请状态。这一可见性仅适用于最小状态结果，不能作为读取完整申请、下载附件或完成注册的授权。

### 6.3 失败与并发

输入格式错误显示字段错误；没有记录是正常“未查到”结果，不冒充网络失败。网络或服务错误显示重试；查询频率过高显示明确等待提示。

请求进行中禁用重复操作。邮箱更改、新查询或卸载时用请求代次拒绝迟到结果，不能把上一邮箱的结果展示到新输入下。请求结果不自动轮询；查询不得发邮件、改变审核或邀请状态、消耗码、更新发送冷却或创建记录。

查询与业务响应使用 no-store，日志不记录完整申请内容、文件字节和凭证。具体限流和错误码随 Contract 固化。

## 7. 分层、依赖与 Contract 切换

| 层                     | 本次责任                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `packages/components/` | 两类表单、分组摘要、文件选择、Modal、查询输入与结果展示；接收 props 和回调，不调用 API    |
| `apps/web/`            | 两个前端路由、展示文案与链接配置、步骤和 Modal 流程、API Client、提交与查询请求、成功导航 |
| `apps/mock-server/`    | 完整输入验证、邮箱唯一、资料与附件事务、最小查询结果、完整审核详情与附件读取              |
| `api/openapi.yaml`     | 申请提交、查询、审核扩展与附件读取的唯一 HTTP Contract                                    |
| `packages/api-client/` | 重新生成 Contract 类型并保持现有 Client 工厂边界                                          |

现工作区的 API 仍为旧直接注册基线，既有邀请注册 RFC 定义了切换方向；ExWebsite 主工作区的最新邀请注册 Contract 已定义三字段 `submitJoinApplication`。开发时先核对并衔接最新邀请后端，避免重新实现或覆盖另一任务的生命周期工作。本文不通过 Git 合并或重写现有实现来掩盖这一依赖。

把三字段请求扩展为两套必填资料，并修改重复申请结果，是公共契约与数据规则变更，必须显式评审与版本化。后续 RFC 需提出具体版本切换和兼容边界，不私自保留可以绕过完整申请的三字段后门。

落地遵守固定顺序：确认业务模型并更新 `.ai/databases/data-model.md` → 修改 `api/openapi.yaml` → `pnpm api:lint` → `pnpm api:generate` → 新 schema/migration、handler 与生成 Client 接线 → 类型检查、测试与构建。服务启动不迁移、不清理数据库、不 reset。

通用表单交接独立于申请业务；可复用可用的通用组件，但本次主线不扩大成动态表单平台。技术 RFC 明确字段定义和消费边界，不要求修改或发布 ExUI 才能验证申请行为。

## 9. 选择理由与范围排除

选择左右说明与入口布局，是为了让长说明易读、两个申请按钮容易找到；窄屏前置入口保持操作可达。未选品牌大首屏或手册目录布局。

选择两份业务 schema 与共用字段定义，保留旧完整内容，又让两类资料与校验边界明确。未选仅三个字段，也未选复制旧 UI 与请求实现。

选择一次事务保存资料与 SQLite BLOB，满足已确认的原子提交及仓库数据边界；未选提前上传的数据库草稿或另设附件文件目录。代价是需要明确大文件请求与并发预算。

选择邮箱直接查询，符合已确认的低操作成本；接受最小申请状态可由知晓邮箱者查询的产品决定。未选查询验证码，不让状态查询赋予注册或资料读取权限。

本期不实现真实邮件投递、生产 PHP/MySQL、面试排期、课程系统、完整权限后台、批量审核、申请修改、动态表单编辑器、浏览器草稿持久化或 ExUI 发布。
