# 通知功能与 UI 优化设计

日期：2026-10-09

状态：交互方向与移除恢复/撤销的范围已确认；本文待最终审阅。本文不授权代码实现、提交或部署。

模块目录：`.notes/notifications/`。后续 RFC 位于 `.notes/notifications/rfcs/`。

## 1. 目标与确认范围

简化已有持久通知体验，覆盖 Website 顶栏 Popup、通知历史 Modal、列表分页，以及恢复功能涉及的 Contract、Client 和 Server。

1. Popup 删除“打开面板不会自动标为已读。”及其独立底部区域/分隔线。
2. 删除恢复清理记录面板、恢复按钮、清理后的撤销入口及其 API、状态、组件和业务实现。用户已确认清理后不能恢复。
3. “全部 / 未读”使用 ExUI Tab，同一行最右侧只有一个批量按钮。
4. 有全局未读时，按钮显示“已读全部”；全局未读为零时，显示“清理全部”。
5. 不显示“已加载 N 条”，不以已加载的行数暗示通知总数。
6. 通知历史列表按每页 20 条加载，滚动到底部自动请求下一页。
7. 正文未选中态删除原标题和长说明，改为通知图标及一段短文案，在正文可用区域水平、垂直居中。
8. 通知历史使用 ExUI 响应式 Modal：桌面两栏，手机全屏；手机列表与正文在同一个 Modal 内切换。
9. Header Bar 铃铛在已确认全局未读数为零时不显示计数 Tag；有未读时显示计数。

通知事件、发布、偏好、授权与正文安全策略沿用现有实现。本次不涉及 Outline 的通知系统，不新增通知路由。

## 2. 当前证据与方案选择

当前结构：

- `api/openapi.yaml` 已有 `listNotifications` 游标分页、全局 summary、批量已读、清理预览、精确清理、清理批次列表与恢复 operation；当前 Contract 版本为 `0.5.0`。
- `apps/web/src/notifications/useNotificationsController.ts` 管理 API 和状态，每页 20 条；当前通过“加载更多”触发分页，分页失败后丢弃游标并允许重读第一页。
- `packages/components/src/notifications/NotificationBell.tsx` 提供最多 5 条未读预览与“查看全部”。
- `packages/components/src/notifications/NotificationHistoryModal.tsx` 当前手工组合 Dialog、Select、批量按钮、恢复面板和确认弹窗。
- 已安装 registry 包 `@exre/exui` 为 `0.8.0`；公开 `ModalProps` 提供 `width`、`height`、`padding`、`mobileFullscreen`、关闭策略和焦点回调。手机全屏断点为小于 768px。
- `.ai/databases/data-model.md` 表明清理批次还承担精确快照、状态版本核验与命令事实保存，不能随恢复 UI 一起删除。

选择在现有模块边界内调整：沿用游标 API 和清理快照，ExUI 负责弹窗框架，Website 控制器负责请求与状态，共享组件负责 Tab、列表和正文呈现。

比较过的替代方向：

| 方向 | 取舍 |
| --- | --- |
| 沿用现有 API，精简恢复链路，替换 Modal 与列表交互（采用） | 符合全部已确认需求，复用授权、幂等和快照行为。 |
| 只隐藏恢复 UI，保留恢复 API 与 Server 实现 | 会留下用户明确不需要的能力，不采用。 |
| 重建通知页面、移动端 Sheet 或分页协议 | 增加独立入口与状态同步成本，当前需求不需要。 |

## 3. Popup 与历史入口

Popup 保留标题“未读通知”、最多 5 条预览和“查看全部”；删除底部说明及只服务该说明的样式和文案定义。

Header Bar 铃铛的计数 Tag 依据全局未读数：已就绪且为零时不渲染 badge 节点，保留可点击的铃铛；大于零时沿用现有计数上限文案。即使还有已读历史，未读为零仍不显示 Tag。加载/错误不等于已确认零通知，沿用现有状态提示；辅助技术可读名称仍反映计数或未知状态。

自动分页用于完整历史 Modal；Popup 继续承担简短预览。点击 Popup 通知时关闭 Popup、打开 Modal 并加载该通知正文。两个交互层不同时抢占焦点。

打开 Popup 或 Modal 不改变阅读状态。用户主动选择通知并成功呈现正文或安全纯文本回退后，沿用现有自动标为已读行为。不会自动选择第一条通知。

## 4. Tab 与单个批量按钮

桌面工具行位于左侧列表顶部；手机列表页中占满可用宽度。左侧为“全部 / 未读”Tab，右侧为一个紧凑文本按钮，始终保持同一行。

- “全部”请求 `view=history`，包括未清理的已读、未读和过期历史。
- “未读”请求 `view=unread`。
- 切换 Tab 清除当前正文选择，回到该列表顶部，并读取该筛选的第一页；旧请求不能覆写新列表。
- 按钮依据服务端全局未读数，不能依据当前 Tab、已加载条目或当前页面是否包含未读来判断。
- summary 已就绪且未读数大于零：显示“已读全部”，作用于全局未读的签名上界，不受筛选或分页影响。
- summary 已就绪且未读数为零：显示“清理全部”，作用于清理预览确定的全部未清理历史，不受筛选或分页影响。
- summary 初次未就绪且没有可靠计数时，保留按钮位置并以禁用的“加载中…”呈现；计数读取失败时禁用按钮，允许沿用已有计数展示，但不能据未知状态执行清理。
- 全部历史已确认无可清理项时禁用“清理全部”；不能用空的“未读”Tab 推断历史为空。
- 批量操作准备或提交过程中防重复点击；准备失败解除禁用。操作期间按钮保持当前操作语义，结果重新读取后再切换。

Tab 使用可访问的 tablist、tab 和 tabpanel 语义，支持键盘操作。右侧批量按钮不作为第三个 Tab。

## 5. 批量操作与清理边界

保留现有批量已读确认和清理预览确认。清理确认使用服务端预览条数，文案为“清理这 N 条通知？”，补充“清理后无法恢复。之后到达的通知会保留。”；零项预览不执行清理，刷新列表并提示暂无可清理通知。

清理仍只改变本人收件状态，不物理删除源内容、事件或业务记录，也不顺带写入已读状态。精确预览集合、clear revision 核验、签名 token 到期与 `requestId` 幂等继续保留；两份仍有效的清理预览各自独立。

新到通知超过本次批量已读的签名上界时保持未读；不在清理预览内的新通知继续保留。如果确认期间到达新未读，本次清理仍只作用于已预览集合，不扩大范围、不自动标为已读。

请求失败保留原 UI 状态和可重试意图，重试同一提交使用原 `requestId`。提交结果不确定时不通过乐观删除伪造成功。预览过期后停止提交，提示重新预览。

执行成功后重新读取 summary、Popup 未读和当前 Tab 第一页；清理成功还清空正文选择。普通结果反馈使用 ExUI `ExMessage` 的已有全站宿主，不再生成带撤销按钮的底部状态区。持续错误与重试入口留在对应列表、正文或确认界面。

## 6. 自动分页与请求生命周期

使用列表末尾 sentinel 及 `IntersectionObserver`，观察根为列表自己的滚动容器。首次加载仍使用现有骨架；后续加载只在列表尾部显示“正在加载…”，不替换已有通知。

自动加载条件同时满足：Modal 打开、列表面板可见、当前第一页已就绪、存在 `nextCursor`、末尾进入可见区、无同筛选列表请求在途、分页不处于错误暂停状态、无阻塞的批量操作/确认。

- 请求按 `(会话、筛选、列表代次、游标)` 去重；控制器在调用开始时就设在途保护，不能只依赖下一次 React 渲染禁用。
- 第一页和后续页通过统一的列表生命周期管理，Popup 的未读读取不能覆盖同筛选的在途翻页结果。批量操作后重读第一页必须淘汰此前的分页响应。
- 用 `receiptId` 去重追加条目，保持服务端最新优先顺序。
- 首屏不够填满滚动容器时，可以逐页串行加载直到末尾离开可见区或没有下一页。
- 每页成功后重新检查末尾是否可见；不能只等 observer 再次跨越阈值，否则连续短页会卡住。
- 没有下一页时停止观察触发，不展示“已加载 N 条”或额外的结束说明。
- 关闭 Modal、切换 Tab、刷新第一页和退出/切换账号时，旧列表请求失效；旧结果不得追加或更新当前列表计数。卸载时解除 observer。
- 手机进入正文后暂停列表自动加载；返回列表恢复原滚动位置后再启用观察。

分页失败保留所有已加载条目，暂停自动触发，在末尾显示错误和一个重试按钮。沿用当前失效游标恢复策略：丢弃失败游标，重试从第一页取得新游标；请求期间仍保留旧列表，成功后替换为新的第一页并恢复滚动位置到顶部，失败继续保留旧列表。文案明确为“重新加载通知”，不能声称只重试下一页。

服务端当前会在个人上界发生变化时拒绝旧游标，因此分页中到达新通知也可能进入上述恢复路径。本次不改变该服务端校验规则，也不引入自动无限重试。

## 7. 正文空态与通知正文

未选中状态仅显示 `lucide-react` 的 `Bell` 图标和“点击通知查看内容”，删除“选择通知”标题及“左侧是全部未清理历史。选择通知后，在这里查看正文与行动。”。

空态容器填满正文可用区域；图标与短文案整体水平、垂直居中，不因正文列的 `align-items: flex-start`、padding 或 flex 收缩而偏到左上角。图标为装饰元素，短文案提供可读内容。

选择通知后的标题、元信息、正文、操作与失败重试沿用现有行为；正文按正常阅读方向排版，居中只用于未选择空态。继续使用已有安全 HTML 呈现与纯文本回退，不修改正文策略。

## 8. ExUI Modal 与手机体验

用公开 `Modal` 替换手工组合的历史 Dialog 框架，标题为“通知历史”，不传说明文本，关闭按钮名称为“关闭通知历史”。

- 桌面首选宽度使用 `size="xl"`，首选高度使用 `height="min(48rem, calc(100dvh - 2rem))"`，由 Modal 约束视口；主体 `padding={0}`。
- 显式启用 `mobileFullscreen`。小于 768px 时全屏，无外圈留白；列表/正文切换也采用同一断点，删除现有 42rem 的弹窗几何覆盖。
- 同一个 React 组件树跨断点适配，不因宽度变化重新创建 Modal 或丢失当前选择。
- 桌面左右两栏分别滚动，Modal 外框不产生第三个滚动条；主体 class 在 ExUI 公开扩展点上建立可收缩的高度链，针对该实例处理外层 body 滚动，不修改 ExUI 包源码或全站其他 Modal。
- 手机初始显示列表；选中通知显示正文与“返回列表”；从 Popup 选中某条通知进入 Modal 时直接显示该正文。
- 返回列表恢复原滚动位置并将焦点还给所选条目；若条目因为已读等原因从当前 Tab 消失，焦点回到该列表的 Tab。
- 关闭返回顶栏铃铛；关闭策略交给 ExUI。批量请求提交期间通过 `dismissible` 阻止重复退出，所有结束路径恢复关闭能力。
- `apps/web/index.html` 的 viewport 加入 `viewport-fit=cover`，让 ExUI 的安全区样式获得有效 inset。
- 几何与收缩使用 CSS Modules 和已有 ExUI token，不增加本地 token 层或重复导入全局样式。正常与 reduced-motion 下的转场使用 ExUI 内建表现，不新增动画库。

## 9. 移除恢复的 Contract 与存储处理

删除以下 HTTP 能力及对应 `serviceHandlers` 登记：

| 方法与 Contract 路径 | operationId |
| --- | --- |
| `GET /notifications/clear-batches` | `listNotificationClearBatches` |
| `POST /notifications/clear-batches/{batchId}/restore` | `restoreNotificationClearBatch` |

删除仅供这些 operation 使用的批次列表/恢复 schema、handler、service、repository 方法、类型、前端状态、恢复意图和组件 props/export；清理实际仍使用的 `NotificationClearResult` 等 schema 不能误删。相应测试改为验证删除后的路由不再提供恢复能力，保留清理/幂等/授权测试。

更新 clear-preview、clear-all 和共享文案中“可恢复”“撤销”等现行承诺。生成式 Client 通过 `pnpm api:generate` 更新，禁止手改生成类型。清理结果的 `batchId` 继续表示内部清理事实，不产生恢复入口。

删除属于破坏性 Contract 变更。本文提出本次 Contract 从 `0.5.0` 标识为 `0.6.0`，由最终设计审阅及后续 RFC 明确记录删除的 operation 与消费方影响；这只是本次具体版本提案，不新增通用 API 版本策略、兼容端点或迁移代理。Website Client 与 Server 同步更新。

清理批次及 item 表继续支撑精确快照和幂等。既有 migration、历史恢复状态与仅为兼容历史行保留的物理字段不在本次删除范围：不改写已执行 migration，不重写历史行，不执行 reset。应用层不再产生新恢复状态；新的 command kind 仅有 `read_through` 与 `clear`。历史表/约束的允许值保留不代表仍有可调用的恢复能力。物理 schema 的进一步压缩需要另行设计，本次无需 schema migration。

实现前更新 `.ai/databases/data-model.md` 的可恢复语义、命令职责和历史字段说明；功能完成后的持久知识同步须反映实际源码，设计阶段不提前将提案写成已实现事实。

## 10. 验证与验收

实现时验证：

- Popup 中无被删除的说明和对应底部区域，预览与“查看全部”仍正常。
- Header Bar 未读为零时无 Tag/badge 节点（包括仍有已读历史的场景）；有未读时显示计数，全部已读后立即隐藏，后续新通知到达后重新显示。
- Tab 切换请求正确筛选；全局未读位于尚未加载页面时仍显示“已读全部”。空“未读”Tab 在全局未读为零时可清理全部历史。
- summary 未就绪/失败时不能执行错误的批量操作；准备与提交不会重复执行；结果文案无恢复承诺。
- 大于 20 条历史滚动到底部加载下一页，重叠 observer 回调只发一次请求，重复 receipt 不产生重复行。
- 首屏不足一屏、连续短页、最后一页、分页失败/重试、切 Tab/关 Modal/退出账号以及批量刷新时的迟到响应均有行为测试。
- 手机正文返回后滚动与焦点恢复；从 Popup 进入正文不出现空的列表页。
- 正文空态图标和短文案整体居中，选择通知后正文正常排版。
- 删除的 operation 不在 Contract、登记表或生成 Client 中，HTTP 路径不再提供对应能力；真实 HTTP 和原始 handler 输出仍双向覆盖保留的 operation。
- 清理快照不影响新到通知；有效预览独立、重复提交幂等、本人授权及未读计数规则仍成立。

自动检查：`pnpm api:lint`、`pnpm api:generate`、`pnpm typecheck`、`pnpm test`、`pnpm build`。仓库根当前没有 `TESTING.md`，沿用现有 Vitest/contract/browser 约定；数据库测试使用 PostgreSQL Testcontainers，Docker 不可用明确失败，不连接开发库。

真实浏览器检查桌面、390px、767px、768px、长正文、长列表、light/dark、键盘关闭与焦点返回。以坐标验证空态居中、手机 Modal 满视口、无横向溢出和第三个滚动条；jsdom 不能证明这些几何结论。缩放或跨断点改变尺寸后选择与内容仍保留。

本阶段仅完成设计，没有执行实现后的自动检查、浏览器验收、真实 iOS/Android 验收或部署。后续报告分别标明自动检查、浏览器模拟手机和真实设备证据；当前阶段不部署上线。
