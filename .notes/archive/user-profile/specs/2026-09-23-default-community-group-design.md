# 通用社区身份组设计

_日期：2026-09-23_

## 目标与范围

为 ExWebsite 的每个正式用户建立“通用”社区身份组成员关系，使后续社区身份组和站内权限设计有一个可靠起点。这里的身份组不是游戏角色，不映射 FiveM 服务器权限。一个用户以后可以加入多个社区身份组。

本设计只建立一个默认组及其成员关系。不定义权限项、组权限、用户额外权限、管理界面、公开资料页或新 HTTP operation。后续待办见 [社区身份组待办](../../todos/2026-09-23-community-groups.md)。

用户名、QQ、FiveM ID 与头像属于同目录下的[用户基础资料设计](2026-09-23-user-profile-design.md)；它们不包含在本默认组设计中。

## 用户与数据行为

- 系统默认组的稳定标识为 `general`，展示名称为“通用”。展示名称可在未来设计中调整，稳定标识不随展示名称变化。
- 默认组是系统保留组；本期没有修改、删除组或移除其成员关系的入口。它不授予任何特权。
- 新账号仅在邮箱验证码验证成功、正式用户创建时加入默认组。用户创建与成员关系写入同一数据库事务；失败时两者一起回滚。
- 新 migration 创建默认组，并一次性为已经存在的正式用户补齐成员关系。待验证的注册尝试不加入组。迁移保留现有账号、会话、SSO 请求和注册状态，不重置数据库。
- 完成注册后的既有幂等重试仍返回原成功结果，不重复插入成员关系。

## 数据边界

`auth_users` 继续保存账号本身。社区身份组独立保存稳定标识和展示名称；成员关系以用户标识与组标识的组合保持唯一，并通过外键关联。这样不会把多个组编码为用户表中的字符串，也为未来多个组留出空间。默认组本期不承载权限记录。

本地 SQLite 使用新的增量 migration 建表、插入 `general` 并回填现有用户；不改写历史 migration。未来 PHP + MySQL 实现遵循相同的业务规则，物理表名及迁移机制由生产实现决定。根据仓库规则，实施前先更新 `.ai/databases/data-model.md`，再修改 SQLite schema 和 migration。

## 系统边界与失败行为

默认组成员关系是账号创建的不变量。Mock Server 在监听前检查所需表和默认组记录是否存在；缺失时明确提示执行显式 migration，不在启动过程中建表或补数据。注册事务如果无法写入成员关系，则不能留下一个缺少默认组的正式用户。

当前 `api/openapi.yaml` 和 `CurrentUser` 响应保持不变，因为本期没有读取或管理身份组的产品入口。以后展示组信息或配置权限时，先评审并修改 Contract，再同步生成 Client、Mock handler、测试与未来 PHP 实现。

## 验收证据

- 从现有迁移状态增量升级后，原有用户各有一条 `general` 成员关系，原有账号、会话与注册数据仍可使用。
- 全新数据库显式迁移后存在默认组；新用户验证成功时恰好加入一次。
- 注册验证失败或事务失败不留下用户或孤立成员关系；完成注册的幂等重试不产生重复关系。
- 未执行新 migration 的数据库使 Mock Server 在监听前明确失败，不隐式修复。
- 现有 Contract Test、类型检查及构建通过；本期不宣称已实现权限控制。
