# 用户基础资料设计

> 迁移说明（2026-09-29）：本文件保留当时的业务与实现决定；其中旧 `apps/mock-server/` 路径、本地 SQLite Mock 与未来 PHP/MySQL 接管的基础设施描述，已由 `.notes/archive/server-promotion/specs/2026-09-29-server-promotion-design.md` 和 `.notes/archive/server-promotion/rfcs/server-postgresql-migration-rfc.md` 取代。当前唯一 Server 位于 `apps/server/`，使用独立 PostgreSQL `exre`；正文中的旧路径和目标仅作历史记录。

状态：已确认，技术细节交由 RFC  
日期：2026-09-23

## 目标与现状

扩充 ExWebsite 的基础用户资料，使用户可以在网页维护用户名、QQ、头像和 FiveM ID。用户还需要通过 API 获取用户资料 snapshot，并设置用户资料。此设计记录已讨论并同意的产品规则；具体 HTTP operation、文件上传限制和迁移方案还需要在后续 RFC 中确定。

当前仓库的 `auth_users` 只有 `id`、`email`、`nickname`、`password_hash`、`created_at`。注册 Contract 要求 `email`、`nickname`、`password`，`CurrentUser` 返回 `id`、`email`、`nickname`。尚无 QQ、FiveM ID、头像字段，亦无相应的资料编辑或图片上传 operation。因此不能把本设计描述成已实现功能。

## 已确认的资料规则

| 资料     | 规则                                                                                                               | 数据归属                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| 用户名   | 沿用现有 `nickname`，作为显示名称；可重复，不作为登录标识。                                                        | 已在基础用户表中。                                 |
| 邮箱     | 仍是唯一的登录与账号标识；本阶段不提供修改邮箱。                                                                   | 已在基础用户表中。                                 |
| QQ 号码  | 可选，由用户在网页填写；作为公开资料展示。                                                                         | 在基础用户表增加可空字段。                         |
| FiveM ID | 可选，由用户在网页手动填写；格式为 `fivem:数字ID`。当前仅保存用户声明，未经 FiveM/Cfx 验证，不用于身份认证或授权。 | 在基础用户表增加可空字段。                         |
| 头像     | 可选，由用户在网页上传图片；作为公开资料展示。                                                                     | 基础用户表保存头像引用，图片文件存放在文件存储中。 |

QQ、FiveM ID、头像均不是必填注册信息；邮箱是唯一具有全局唯一约束的用户资料。`nickname`、QQ 和 FiveM ID 不因本设计增加全局唯一约束。头像文件本身不存入基础用户表。公开资料的约定不意味着公开邮箱；邮箱仍按现有认证用途处理。

## 用户流程与存储方向

- 用户完成现有邮箱验证注册后，可在网页填写或更新这些可选资料；注册流程不要求提供 QQ、FiveM ID 或头像。
- 用户上传图片作为头像，而不是填写外部图片 URL。本阶段不提供公开用户资料页；“公开”表示以后对外展示这些资料时不把 QQ、FiveM ID、头像视为私有字段。资料编辑及本人完整资料读取须经过认证；头像图片可以公开读取，具体读取 operation 仍需遵守 Contract 边界。
- 本地 Mock 阶段，头像图片可写入固定的本地磁盘目录，并由服务读取返回；基础用户表保存其引用。未来 PHP 生产实现使用已具备的腾讯云 COS，将头像存入 COS，通过自定义 HTTPS 域名提供公开读取链接。现在不接入 COS。
- 本地磁盘图片是用户明确选择的阶段性方案。仓库当前 `AGENTS.md` 的“Mock 数据只保留在本地 SQLite”规则与头像文件需求有冲突；实施前须把头像二进制文件的明确例外、固定目录、重置及版本控制边界写清楚。图片元数据和用户关联仍属于数据库数据。
- 未来切换 COS 时需保留资料读取行为，并设计从本地文件引用到 COS 引用的迁移；本阶段不假设本地磁盘 URL 可直接用作生产 URL。

## 资料 API 设计

新增两项产品 API 能力：获取用户资料 snapshot、设置用户资料。两项能力均作用于登录用户本人。本阶段没有公开资料页，也不通过 API 按其他用户标识读取资料。以后增加公开读取时，应使用只包含公开字段的独立响应，不能把邮箱从本人 snapshot 泄露出去。

现有 `GET /auth/me` 已通过 Bearer 认证读取当前用户，且供网页恢复登录态使用。优先扩展其 `CurrentUser` 响应为本人 snapshot：保留现有 `id`、`email`、`nickname`，并增加可选资料的明确空值表示，使现有读取方可以继续使用原字段。另需增加经过 Bearer 认证的资料设置 operation，允许当前用户更新显示名称、QQ、FiveM ID 和头像；服务端从会话确定用户，不能接受客户端指定要修改的用户。邮箱、用户 ID、社区身份组和权限不属于该设置入口。

QQ 与 FiveM ID 属于文本资料；头像必须上传图片文件。设置资料可以在产品界面作为一次保存动作，但底层图片传输可能需要单独的上传 operation；不能用任意外部图片 URL 代替上传。上传成功、资料引用写入、替换旧头像及失败清理的顺序由 RFC 明确，以避免数据库引用不存在的文件。

上述是能力和契约方向，尚未批准新的具体 endpoint、HTTP method、请求或响应字段。实施前先设计并修改 `api/openapi.yaml`，再运行 `pnpm api:lint` 和 `pnpm api:generate`；Mock Server 只实现 Contract 声明的 operation，前端通过 `@workspace/api-client` 调用。若图片由 Mock Server 提供读取，也必须有 Contract operation，不能绕过 Glue 新建 Fastify 路由。涉及用户表职责和数据规则的变化，要先更新 `.ai/databases/data-model.md`，再修改 Drizzle schema 和新增 migration；不重写历史 migration。

## 系统边界

默认社区身份组是另一条设计线索，见[通用社区身份组设计](2026-09-23-default-community-group-design.md)。基础资料不授予任何社区权限，手填 FiveM ID 也不能作为组或权限的可信依据。

## 后续 RFC 需要确定的细节

以下内容尚未在对话中确定，不在此稿中擅自指定：

- QQ 的输入校验和展示格式；FiveM 数字部分的长度与规范化方式；资料清空和修改的请求语义。
- 头像允许的图片格式、大小和像素限制，文件名与存储引用规则，替换及删除时旧文件的处理，公开读取的缓存与安全限制。
- 本人 snapshot 中各可选字段的空值表示、资料设置请求的局部更新与清空语义，以及头像上传所需的独立传输 operation。
- 从当前账号数据增量升级的 migration 细节，以及以后从本地磁盘迁往 COS 的数据迁移方式。

这些细节应在用户资料 RFC 中逐项收敛，再进入实现；已确认的字段、可选性、公开性和存储方向不应因此被遗漏。
