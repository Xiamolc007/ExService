# 通用配置式表单与加入申请 handoff

- 日期：2026-09-27。
- 状态：申请内容、分步交互与窄屏单列已获用户确认；通用组件的归属和公开 API 为建议，开发前确认。
- 目标：使用少量字段对象、Zod schema、默认值和业务回调生成表单，以两种加入申请作为首批完整消费场景。
- 本交接只新增文档，不代表通用组件、申请页、Contract 或数据库变更已实现，也不授权提交或发布 ExUI。

## 1. 已确认的业务与界面

1. `/join` 是带站点导航的说明页，展示申请解释、加入流程、申请入口和 Q&A。
2. 采用已确认的 A 布局：宽屏左侧说明、流程与 Q&A，右侧放申请入口；窄屏变成一列，顺序为标题与简介、两种申请入口、申请须知与加入流程、Q&A。
3. 保留两个独立入口：全新玩家申请、有经验的玩家申请。分别打开对应的分步 Modal。
4. 旧两套表单的全部资料、题目、选项、承诺和经验玩家的可选证明附件均保留；组件和视觉重新设计，不复用旧 Ant Design 或 `ex-framework` 实现。
5. 全新玩家分为五步：联系方式 → 基本资料 → 玩法认知 → 时间与来源 → 确认提交。
6. 有经验玩家分为六步：联系方式 → 基本资料 → 过往经历 → 笔试与证明 → 时间与来源 → 确认提交。
7. Modal 标题、进度和底部操作保持可见，内容区独立滚动。宽屏可按字段组使用两列，长题目占整行；窄屏全部字段单列，标签可换行，无水平溢出，也不沿用旧页的 480px 最小宽度。
8. 后退保留已填内容，前进校验当前步骤，最终提交校验完整资料与承诺；只有最后一步提交。关闭或刷新清除未提交草稿，不把资料和附件写入浏览器持久存储。
9. 申请提交保存数据库记录，不创建账号。通过审核后接入邮件邀请 → 验证邮箱 → 完善名字与密码 → 注册成功 → 登录的既有设计方向。
10. 同一规范化邮箱只能申请一次，两个申请类型共用去重规则；切换类型或被拒绝后均不能另建重复申请，也不能通过重提交覆盖旧资料。
11. 增加独立申请查询页。用户输入申请邮箱直接查询，无邮箱验证码步骤；公开结果只显示申请状态与下一步，不返回姓名、QQ、出生日期、答题内容、附件或注册凭证。

第 9–11 项由申请业务层负责，通用表单只提供输入、校验和提交接口。

## 2. 推荐的组件归属

建议先在 `packages/components/src/forms/` 实现本站可复用的配置式表单，基于 ExUI、React Hook Form 与 Zod。用两套完整申请验证 API 后，再评估迁入 ExUI 的独立 `forms` 扩展入口，或拆为独立表单包。

| 层 | 责任 | 示例位置 |
| --- | --- | --- |
| ExUI 基础控件 | Field、Label、Input、Textarea、Select、Checkbox、Dialog、主题与 token | 已安装的 `@exre/exui` |
| 通用表单 | 字段配置、控件适配、RHF 绑定、Zod resolver、错误、布局、默认值与方法 | 建议 `packages/components/src/forms/` |
| 申请表定义 | 两类字段、文案、业务 schema、步骤、确认摘要 | 建议 `packages/components/src/join/` |
| 页面与申请流程 | Modal 开关、成功状态、API Client、DTO 映射、查询和导航 | 建议 `apps/web/src/join/`、`apps/web/src/pages/JoinPage/` |
| 后端与存储 | 去重、审核、邀请、附件存取、数据模型与 Contract | `apps/mock-server/`、`api/openapi.yaml` |

通用表单不依赖路由、认证、申请状态、API Client、HTTP endpoint 或 SQLite。上传控件只选择、删除、显示和校验本地文件；附件传输、进度和重试由业务回调适配。RHF 是唯一字段状态来源，避免再创建一份控件值或表单 store。

迁入 ExUI 时，建议采用可选择的扩展入口，例如提议的 `@exre/exui/forms`，同时明确 RHF、resolver 与 Zod 的依赖和支持版本，保证 context 使用同一个实例。该入口当前不存在，不可当作已发布 API 使用。ExUI 库开发、公开类型、打包和发布属于独立任务；此次交接不修改其源码或导出。

## 3. 通用 API 的建议

公开接口以一个配置式组件为主，保留自定义字段出口；以下名称为提案，不是已存在的组件。

- `ConfiguredForm`：接收 schema、默认值、字段组和 `onSubmit`，统一 RHF、错误与布局。
- 字段配置：有类型检查的 `name`、`label`、控件种类、控件参数、说明和列宽。`name` 必须是 schema 输入模型的合法路径。
- 控件适配器：普通输入使用 RHF register；Select、Checkbox、日期、多选和文件使用 Controller 等适配，统一 value、change、blur、ref、disabled 语义。
- 自定义 render：接收绑定信息与字段错误，允许复杂控件组合，仍受统一表单上下文管理。
- 必要方法：读取值、设置值、reset、校验指定字段、设置字段错误和表单级错误、聚焦错误项。可使用 RHF 的既有方法，避免逐项复制成另一套大型 API。
- 步骤层：复用同一个表单实例，按配置显示字段、切换步骤、提供摘要。步骤进度可由外层控制；字段和校验状态留在 RHF。

建议的调用形态如下。示例只展示联系方式组，完整申请还要添加后续章节定义的字段和 schema。它是目标 API 草案，不能直接 import 为现有组件。

```tsx
import { z } from 'zod'

const contactSchema = z.object({
  nickname: z.string().trim().min(1, '请填写名字'),
  email: z.email('请填写有效邮箱'),
  qq: z.string().regex(/^[0-9]{5,13}$/, 'QQ 号码须为 5–13 位数字'),
})

const fields = [
  { name: 'nickname', label: '你的名字', control: 'text' },
  { name: 'email', label: '邮箱', control: 'email' },
  { name: 'qq', label: 'QQ 号码', control: 'text' },
] satisfies FormFieldConfig<z.input<typeof contactSchema>>[]

<ConfiguredForm
  schema={contactSchema}
  fields={fields}
  defaultValues={{ nickname: '', email: '', qq: '' }}
  layout={{ columns: 2, narrowColumns: 1 }}
  onSubmit={onContactConfirmed}
/>
```

`FormFieldConfig` 与 `ConfiguredForm` 为待设计类型。`onContactConfirmed` 由调用方提供。正式名字、邮箱与 QQ 规则须采用业务 schema，并核对生成的请求类型；示例不会替代 Contract。

### 校验与值的边界

1. Zod 是客户端输入校验的唯一来源；字段配置不再维护另一套 Ant Design 风格的 `rules`。必填标记是展示信息，不能独立改变校验结果。
2. 区分 `z.input` 与 `z.output`：默认值、控件和路径绑定原始输入；成功回调接收 Zod 解析后的输出。支持 trim、coerce、transform 等情况时不能把两者强行声明成同一类型。
3. 不从 Zod 内部结构自动猜测标签、选项、步骤、控件或所有必填关系；这些由少量显式配置声明。
4. 步骤前进只阻止当前步骤的错误，不能因未来步骤尚未填写而无法继续。最终提交执行完整 schema，跨字段约束必须真实生效。
5. 不假设任意带 refinement、transform 或 union 的 schema 都能直接 pick 成步骤 schema。步骤字段/schema 策略须显式支持；复用同一组字段 schema，不重复维护验证规则。使用反例测试证明未来字段、跨步骤约束和错误归属正确。
6. 后退或卸载当前步骤保留值；真正关闭整份申请才重置。切换申请类型使用对应独立 schema，经验玩家字段不能泄漏到新手提交中。
7. async `onSubmit` 的 Promise 必须被等待；在途提交禁用重复操作。失败保留草稿，将业务返回的字段错误映射到 `setError`，并显示表单级错误。
8. 文件保留为 `File[]` 等显式输入类型；日期使用明确的日期字符串或适配器值，不能暗中转换成任意 Date/dayjs 对象并改变请求语义。

### 控件范围

首期提供两套申请实际需要的文本、邮箱、长文本、日期、单选、可自由填写的选择、多选、承诺复选框、文件列表及自定义 render。日期和“选择或自由填写”需要与 ExUI 公开控件组合，不引入旧 `ExBirthInput`、`ExSelectInput`。

先支持字段组、纵向标签和响应式列数。后续可扩展横向或 inline 布局。动态重复列表、远端 schema、可视化表单编辑器、数据库保存表单模板和通用流程引擎不是本任务的必要范围。

## 4. 两套申请共用的内容

业务字段名在 Contract 修订时固化。下表保存业务含义，不声明新的 HTTP 请求形状。

| 步骤 | 字段 | 内容与规则 |
| --- | --- | --- |
| 联系方式 | 名字 | 必填；新手显示“你的名字”，经验玩家显示“IC 名字” |
| 联系方式 | QQ 号码 | 必填；旧表校验为 5–13 位数字，前导零作为字符串保留 |
| 联系方式 | 邮箱 | 必填；用于联系、邀请、唯一性和查询；按服务端的 trim、转小写规则规范化 |
| 基本资料 | 出生日期 | 必填；使用合法日期，不接受不存在的日期或未来日期 |
| 基本资料 | 申请人类型 | 必填；普通成年申请者 `100`、普通未成年申请者 `101`、曾任其他服务器管理 `102a`、曾任技术 `102b` |
| 基本资料 | 申请部门 | 必填；警察部门 `leo`、医疗和消防部门 `ems` |
| 时间与来源 | 每周空闲时间 | 必填；可选“每晚都有空”“每周三天以上”“每周三天以下”，也可自由填写 |
| 时间与来源 | 了解方式 | 至少选择一项；可多选 B站 `bilibili`、抖音 `douyin`、朋友介绍 `friends`、其他 `other` |

“全新／经验玩家”与表内“申请人类型”是两个不同维度，不能用同一个字段混合编码。四个申请人类别的值保留在业务数据中；展示不必强调旧编号前缀。

旧表 QQ 的 5–13 位规则与当前账号资料的 1–20 位规则不同。完整保留旧申请时按前者设计，账号资料规则不因此改动；申请 Contract 须明确这一差异。名字和邮箱仍须核对当前 Contract 的边界，不能照搬旧正则作为新的协议。

出生日期、年龄说明与人工审核资格之间的关系由申请业务规则确定，不让通用日期控件写死社区年龄限制。

## 5. 全新玩家的专属内容

玩法认知步骤保留以下五个必答问题。

| 问题 | 输入方式与旧选项 |
| --- | --- |
| 是否接触过 FiveM，是否游玩过其他 RP 服务器？ | 可选择“没有接触过”，也可自由填写 |
| 是否对“紧急职业模拟”这一种游玩方式有过了解？ | 可选择“了解”“不了解”，也可自由填写 |
| 是否对美国警察的执法程序有基本了解，或对紧急救援和医疗处理的流程有基本了解？ | 文本回答 |
| 是否知道什么是 RP？ | 文本回答，提示“谈谈你对 RP 的理解” |
| 是否知道什么是 FRP？ | 文本回答，提示“谈谈你对 FRP 的理解” |

确认步骤展示全部资料的只读分组摘要，允许返回对应步骤修改。以下三项均须明确勾选。

1. 我确认以上信息真实无误。
2. 我能保证遵守服务器内所有规定与政策。
3. 我清楚：面试通过进入学院后，因自身原因导致缺课、旷课等行为所带来的后果由自己承担。

承诺保存在 RHF 中，Zod 要求 true；不能再用独立 `useState` 控制三个确认值。服务端如何记录承诺及版本由申请 Contract 与数据模型设计明确。

## 6. 有经验玩家的专属内容

### 过往经历

以下六项全部必填。

1. 以前所在服务器。
2. 离开原本服务器的原因。
3. 以前所在部门：可以自由填写，也保留巡逻部门、交通部门、特殊部门、警探部门、飞机部门、医疗部门、消防部门这些选项。
4. 在其他服务器的执法生涯经历。
5. 以前所在服务器最高警衔／等级。
6. 是否被以前服务器有过任何形式的处罚：无处罚也须明确填写。

### 笔试与证明

| 内容 | 要求 |
| --- | --- |
| 你认为警员在执法过程中是否需要遵循“武力降级”原则？如果是，为什么？ | 必填，不少于 150 字 |
| 你认为在什么样的情况，警员可以使用“自由裁量权”？ | 必填，不少于 150 字 |
| 你认为为什么我们应该接受您的调转？ | 必填 |
| 证明文件 | 可选，最多 5 个，每个不超过 10 × 1024 × 1024 字节，支持选择、拖放及粘贴文件 |

两道题原文要求“不少于 150 字”，旧组件只实现必填；新表单必须补上长度校验，不能复制这一遗漏。建议按去除首尾空白后的 Unicode 码点计算；正式字数、文本最大长度及服务端规则在申请业务 RFC 中统一。

保留旧附件类型：`.png`、`.jpg`、`.jpeg`、`.gif`、`.bmp`、`.svg`、`.pdf`、`.doc`、`.docx`、`.xls`、`.xlsx`、`.ppt`、`.pptx`、`.txt`、`.zip`、`.rar`、`.7z`。

通用控件显示文件名、大小与移除操作，校验数量、单个大小和允许类型；浏览器筛选不等于服务端校验。实际存储、读取权限、失败补偿及内容处理交给业务层。当前仓库只允许头像作为本地 SQLite 之外的文件例外，不能直接把证明文件写入新的本地附件目录；存储方案须另行固化，或先获得对这一仓库边界的明确修订。

确认步骤展示完整分组摘要与附件清单，须勾选“我确认以上信息真实无误”。经验玩家不额外复制新手专属的两项承诺。

## 7. Ant Design Form 的参考方式

用户指定 [Ant Design Form 中文文档](https://ant-design.antgroup.com/components/form-cn/) 为参考。此次核对使用其 [官方中文站同一组件文档](https://ant.design/components/form-cn/)。

参考其 Form / Form.Item 分层、默认值、字段错误、方法调用、Modal 表单、依赖字段、错误定位和销毁语义。官方 Form 主要通过字段组合工作，“字段对象 → 自动生成控件”是这里提出的配置层，不应宣称为官方 Form API 的直接复刻。

本站已经要求 RHF、Zod 与 ExUI，继续采用这套状态和校验机制。借鉴使用体验，不安装 Ant Design 或 rc-field-form，也不实现另一份 store 或 rules 校验系统。

## 8. 与当前申请实现的接线边界

目标仓库的 `api/openapi.yaml` 已声明 `submitJoinApplication`，当前申请请求是邮箱、名字与 QQ。其 `.notes/archive/join-registration/rfcs/join-registration-rfc.md` 仍描述三字段申请、整页分步表单及拒绝后重新申请。上述内容尚不能完整承载此次确认的两套表单、Modal、全历史邮箱去重与公开申请状态查询。

本 handoff 记录新的产品要求，不能静默覆盖目标仓库正在进行的申请后端工作。开发时分开完成以下工作。

1. 先交付不依赖 API 的通用表单组件，并以组件测试和静态示例证明字段、校验和分步行为。
2. 用两个独立的业务 schema／字段配置实现全新与经验玩家表单。共享基础字段定义、控件与错误处理，不复制整套组件。
3. 再协调申请业务设计，修订 `.notes/archive/join-registration/` 中的设计及 RFC，明确完整字段、承诺、附件、去重与状态查询。
4. 按仓库规则先更新并评审 `.ai/databases/data-model.md`，然后修改物理 schema 与新增 migration。
5. 先改 `api/openapi.yaml`、执行 `pnpm api:lint` 与 `pnpm api:generate`，再接入后端 handler 和 `apps/web/` 的生成 Client。不能把表单配置或客户端 Zod 当作第二份 HTTP Contract，也不能发送 Contract 未接受的字段。

通用组件开发不要求先实现审核或文件服务；完整业务验收则必须覆盖真正提交后存储、两类共同去重、公开查询与邀请注册衔接。未完成 API 接线的组件示例不能报告为申请闭环通过。

## 9. 验收要求

- [ ] 新建一个简单表单只需要 schema、字段对象、默认值及提交回调；标签、错误与绑定不必逐个重复手写。
- [ ] 字段路径有类型检查；自定义渲染与内置控件均连接同一个 RHF 实例。
- [ ] schema 的输入、输出和 transform 保持正确类型，最终回调只能得到成功解析的数据。
- [ ] 两套申请完整包含第 4–6 节列出的内容，名字标签、选项、自由填写、多选和承诺正确。
- [ ] 当前步校验、未来字段未填、跨字段约束、后退保留值、最终全量校验均有行为测试。
- [ ] async 提交期间不会重复提交；失败保留输入，字段错误与表单级错误可见。
- [ ] 类型切换或关闭后不泄漏另一份草稿；没有 localStorage/sessionStorage 草稿或文件持久化。
- [ ] 文件的数量、大小边界、允许类型、拖放、粘贴和删除可验证；对实际上传失败的行为由业务接线测试覆盖。
- [ ] 宽屏两列与窄屏单列都有浏览器验证；至少检查 320px、375px 与桌面宽度，长题目、长错误和文件名不造成横向溢出。
- [ ] Modal 标题与描述、焦点恢复、键盘、错误关联、第一错误定位及长内容滚动可用；不遮挡底部操作。
- [ ] 两类邮箱共同去重及查询敏感字段隔离由 Contract HTTP 与注册 handler 原始输出测试验证。
