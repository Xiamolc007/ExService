# 普通身份隐含，管理员身份显式记录

- 状态：已接受
- 模块：`server`
- 日期：2026-09-24

## 背景

原模型为每个正式账号写入 `general` 成员关系。该关系对所有正式账号均成立，当前又没有组信息读取或权限判断入口，因而不提供额外的业务区分。用户决定让普通身份成为已认证正式账号的默认状态，只持久化被明确授予的管理员身份。

## 决策

- 不再为注册成功的账号写入 `general` 成员关系；正式账号没有显式组关系时按普通身份处理。匿名请求必须先通过认证，不能因没有组关系而取得普通用户权限。
- 保留组表和成员关系表，以 `admin` 作为系统保留组。注册不授予管理员身份；未来的授予和撤销须由受信任的管理流程完成。
- 当时的 SQLite 增量 migration 移除了已有 `general` 成员关系与组记录，建立 `admin` 组，并保留其他显式组及成员关系。当前 PostgreSQL 从空库建立基线，只创建 `admin` 组，不导入旧 SQLite 账号或成员关系。
- 本次不定义管理员初始化、具体权限目录或 HTTP 管理入口。`admin` 成员关系尚未被任何权限判断使用。

## 理由与取舍

省去对每个普通用户都相同的关系写入，也避免把默认身份当成可撤销的组成员关系。显式关系仍由外键和组合主键约束，未来若有其他需授予的组，可以沿用同一模型。相比在 `auth_users` 存放组编码数组，关系表可以约束组是否存在并防止重复成员关系；代价是需要关联查询和独立管理组定义。

旧 SQLite 增量迁移删除了原有 `general` 记录；若外部工具曾依赖这些记录，须改为根据已认证的正式账号判断普通身份。当前 PostgreSQL 空库基线没有旧成员关系，且没有管理员授予流程，因此初始没有管理员成员，符合默认不授予特权的规则。

## 重新审视的条件

实现首个需要管理员权限的 operation 前，必须明确管理员初始化、授予与撤销权限的主体，以及检查会话和组关系的时机，并先更新 HTTP Contract。若引入更多特殊组，再定义各组的权限含义及组合规则。
